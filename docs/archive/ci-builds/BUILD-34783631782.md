## Evidence corrections (reporting, not code)

### Clearing `armed` is a deactivation request, not an acknowledgment
How ARM observes the write: `riivo_di_read` performs one plain aligned
word load of the params word per call and branches on it; there is no
acknowledgment path back to the PPC side. In-flight reads are benign by
structure, not by locking: the DIP thread is synchronous, so a read
either loaded `armed` before the PPC's flush (MISSES, stock boot) or
after (serves); the word itself cannot tear. Backing memory is never
reused or freed during the boot — the reservation is lowered once and
stays lowered — so there is no use-after-free window to close, only the
visibility question below.

PPC flushing alone does NOT establish ARM-side cache visibility, and the
late `0 -> 1` arm transition is observability-pending: the `armed` word
sits in a params line the ARM side otherwise only reads, so if Starlet
holds that line from the unarmed reads, the ARM core may keep seeing `0`
after the PPC's flush lands in MEM2. That failure runs in the safe
direction (endless MISS to stock, visible in the miss counter, never a
served stale byte) but would present as a silently inactive mod. The
candidate fix — invalidate (never clean: ARM dirties nothing on that
line, all ARM-written counters sit on the adjacent line) the params
line before the armed load — is NOT in this build. Until hardware shows
the transition, treat late arming as unproven even though every other
leg (fill, verify, poison, refusal) is host-pinned.

### GateModel is modeled lifecycle coverage
`test_segread`'s GateModel section reimplements the three-line ARM gate
(no init call, no reader state while unarmed) on the host and drives the
REAL `sr_init`/`sr_read` through it (no init pre-arm, exactly one init
post-arm, poison refusal, deactivation stop). That pins the transition
contract the ARM code implements line-for-line; it does NOT execute
`riivo_di_read`/`riivo_ios_init` themselves — PPC-view address masking,
live d2x device routines, and Starlet cache behavior remain
hardware-only, as stated wherever the module boundary appears.
